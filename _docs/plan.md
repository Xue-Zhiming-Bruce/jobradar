# JobRadar — Plan

## Goal

A daily digest of new job postings at companies you actually want to work for,
matched against your resume, with a plain-English reason for each match.

## Users

One user: the owner. No accounts, no login, no multi-tenancy.

## Problem

Finding relevant openings means checking many company career pages by hand, or
drowning in a job-board firehose where most postings are irrelevant. Neither
tells you *why* a role fits, so you re-read the same postings repeatedly.

## Behavior spec (MVP)

1. **Resume upload.** `POST /resume` accepts a file, extracts plain text, stores
   it as the active resume. Rejects wrong type/oversized files with a clear
   error. Resume contents are never committed, never logged.
2. **Watchlist.** Add a company by name, board slug and source, Greenhouse when
   the source is absent. List and delete. Duplicate slugs are rejected.
3. **Poll.** `POST /internal/tick` (shared-secret header) walks the watchlist,
   fetches each company's public job board, normalises postings,
   and upserts them. Re-running is idempotent: a posting seen before is not
   inserted twice and does not alert twice. The tick starts its work as a
   background task and returns `202` immediately, writing a run row the UI
   reads for progress — a tick that scores many postings must not outlive an
   HTTP timeout.
4. **Score.** New postings pass a deterministic prefilter (title/seniority/
   location/must-have keywords). Survivors get one LLM call returning
   structured output: score 0–100, why it fits, what is missing. Postings
   below the configured cutoff are stored but not alerted.
5. **Digest.** New postings above the cutoff are grouped and emailed. If
   nothing qualifies, no email is sent and the run is recorded as "no new
   matches".
6. **Web UI.** Manage the watchlist; browse matches with score, reasoning and
   gaps; mark a match saved or dismissed; a **"Run digest now"** button so the
   digest never depends on a scheduler firing.

## Non-goals (MVP)

- LinkedIn and Indeed ingestion. Both are partner-gated and scraping breaches
  their terms. Documented in the README as a deliberate decision.
- Manual "paste a JD" intake.
- Embeddings or a vector store. Only if LLM match quality proves insufficient.
- Instant/per-posting alerts.
- Auto-apply, cover-letter generation, interview prep.
- Multi-user accounts, sharing, or permissions.
- Workday and other enterprise ATS providers (XML, messier shape).

## Architecture

- **Frontend:** React, all backend calls centralised in one API module.
- **Backend:** FastAPI, endpoints per the OpenAPI contract it generates.
- **Matching:** behind one `MatchScorer` interface — prefilter plus LLM
  structured output. Tests use a fake scorer, so the suite needs no API key.
- **Storage:** SQLAlchemy over SQLite locally and Postgres in production.
- **Packaging:** one container. The frontend build is served as static files by
  the backend, so there is no CORS and one URL to review. The poller is an
  endpoint, not a second service.
- **Deploy:** Render free web service (Docker) plus Neon Postgres, decided by
  Jev — see `_docs/decisions/2026-10-11-deploy-and-repo.md`. A scheduled GitHub
  Actions workflow calls `/internal/tick` as a convenience; because Actions cron
  drifts and can skip, the UI button is the reliable path.
- **CI/CD:** GitHub Actions runs the test suites, and deploys when they pass.
- **Repository:** public on GitHub, decided by Jev so peer reviewers can read the
  code. Nothing private is ever committed; resume uploads are stored outside the
  repository and never logged.

## Known constraints

- Render free instances spin down after 15 minutes idle and take about a minute
  to wake. The README says so, so a reviewer is not surprised.
- Free tiers sleep and cron drifts. The digest is therefore also reachable on
  demand, which is what the demo relies on.
